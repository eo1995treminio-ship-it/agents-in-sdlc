最初に、小さな機能をプロジェクトに追加しました。より大きな変更には、さらにしっかりとしたプロセスが必要です。GitHub Copilot app は組織で使われている既存の流れに合わせて作業できるため、正しい方法で必要な機能を構築できます。このレッスンから、エージェントを使った一般的な開発プロセスを始めます。Issue から新機能を作り、コードの妥当性と機能の動作を確認し、最後にプロジェクトへマージします。

> [!NOTE]
> 機能開発を続ける間、同じセッションを使います。通常は作業対象ごとに別のセッションや PR を作りますが、ここでは主な概念に集中するため手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub Issue からエージェントの新しいセッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで機能を実装します。
- コードをレビューします。
- ブラウザー Canvas で機能を手動で検証します。

機能の作業を続けながら、リポジトリの instruction を更新し、既存の `quality-checks` skill をカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、利用者はカテゴリや発行者でゲームを絞り込む必要があります。バックログの Issue には機能が記載されていますが、カテゴリを組み合わせる方法など、コーディング前に合意が必要な詳細があります。Plan モードで決定し、範囲を定めた実装を Autopilot に許可します。

## 背景

AI コーディング エージェントを開発プロセスに導入しても、基本は変わりません。むしろ、基本がさらに重要になります。多くの開発者は、次のような流れで作業します。

1. 必要な作業の詳細を記述した Issue を開きます。
2. 構築する内容を計画します。
3. コードを作成してレビューします。
4. テストを実行し、コードを検証します。
5. 新しい機能を手動で検証します。
6. プルリクエスト（PR）を作成します。
7. コードがレビューされ、継続的インテグレーションの処理が成功したら、コードを merge します。

> [!NOTE]
> 詳細な手順はチームや組織によって異なりますが、多くの場合は上記の流れを調整したものです。

この標準的な方法に従うと、AI が生成したコードが要件を満たし、手作業で書いたコードと同じレビュー プロセスを経ることを確認できます。

## セッション モード

**セッション モード**は、エージェントにどの程度の自律性を与えるかを制御します。プロンプト欄の下にあるドロップダウンで設定でき、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、次に進む前にユーザーの入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。エージェントが実行する前に、計画をレビューして承認します。
- **Autopilot**: エージェントはコードを書き、テストを実行し、入力を待たずに反復して自律的に作業します。

まず Plan モードで計画を確認し、その後 Autopilot で実装します。

## Issue からセッションを開始する

開始する前に、星評価の PR が merge され、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリ フォルダーを選択し、リポジトリ上部のナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。テンプレートに含まれる Issue なので、新しく作る必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

    ![Issue ビューの New session ボタンを矢印で示した GitHub Copilot app の画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モード選択で **Plan** を選びます。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションで見つからない場合は、app の PATH またはバージョン管理ツールの設定を確認し、app を完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで再インストールしないでください。

## フィルタリング機能を計画する

計画を立てると、Copilot がコードを書く前に、実装方法を確認できます。Issue から始めたため、機能の依頼内容はすでにコンテキストに含まれています。次の prompt を送信します。

```plaintext
Build this feature.
```

Copilot の質問に答え、計画を Issue の受け入れ条件と照らし合わせます。カテゴリと発行者によるフィルタリング、アクセシブルなコントロール、データ アクセスの変更、テストが含まれていることを確認します。複数カテゴリの組み合わせ方や、該当するゲームがない場合の動作など、不明確な点を相談します。

計画には、既存のプロジェクト ツールを使った lint、ユニット テスト、E2E テスト、型チェックを含めます。フィルタリングの実装とテストに範囲を絞り、品質ワークフローを終えてから PR を作成します。承認前に計画の修正を依頼し、後で検証できるよう Issue の URL と合意した説明を控えておきます。

## Autopilot を明示的に承認する

計画に問題がなければ **Approve and implement this plan**、または使用中のバージョンに表示される同様の項目を選択します。承認によってモードが自動的に切り替わるとは限らないため、現在のモードを確認します。モード表示が **Autopilot** であることを確認してください。

Copilot は実装を始めます。計画に沿って作業し、コードを生成してテストを実行する様子を確認できます。

> [!NOTE]
> 承認すると、すぐに実装が始まることがあります。先に計画をレビューしてください。依存関係が不足している、またはポートが競合していると Copilot が報告した場合は、チェック完了と判断する前にセットアップの問題を解決します。自分が起動したサーバーだけを停止してください。

## 実装をレビューして検証する

コードの生成後は、ほかのコードと同じように merge 前にレビューします。コードを確認し、サイトを起動して問題がないか検証しましょう。

1. **Changes** を開き、フィルタリングの実装とテストを調べます。
2. 結果を Issue と承認済みの説明に照らし合わせます。複数のカテゴリと発行者の組み合わせを確認し、リポジトリの instruction に従っていることも確かめます。
3. lint、ユニット テスト、E2E テスト、型チェックの出力を調べます。チェックがスキップされている場合は成功ではありません。
4. 失敗を解決し、実装を受け入れる前に該当するチェックを再実行します。Playwright の E2E 設定は preview をビルドして実行し、ローカル サーバーを再利用することがあります。テスト対象が前のレッスンのサーバーではなく、この worktree のサーバーであることを確認してください。

## 新機能を試す

コードに問題がないことを確認しました。次は実際に動かします。前と同じようにアプリを起動し、ブラウザー Canvas で Web サイトを開きます。

1. 次の prompt で、アプリを起動してブラウザー Canvas にページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザー ウィンドウが開きます。
3. カテゴリを選び、結果が一致することを確認します。フィルターを解除してから発行者を選び、結果がその発行者のゲームと一致することを確認します。
4. カテゴリと発行者のフィルターを組み合わせ、Issue と承認済みの計画と結果を比べます。複数カテゴリがサポートされる場合は、合意した組み合わせの動作を検証します。
5. 該当するゲームがない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットし、一覧全体が戻ることを確認します。
6. 確認が終わったら、次の prompt でこのセッションが起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンに向けてセッションを保持する

フィルタリングの PR はまだ作成または merge しないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次は custom instruction をフィルタリングのコードに適用し、skill と QA を改善してから、レッスン 8 でまとめた PR を作成して merge します。開発サーバーを停止した後は、セッションを終了せずに待機させます。次のレッスンで同じセッションに戻ります。
